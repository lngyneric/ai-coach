# P2 · 企业课型分类模板（Lesson-Type Templates）

> 配套 skill：`ai-shifu-course-creator`（生成）/ `course-designer`（设计）
> 入口：`docs/P1P2-DESIGN.md` §1 决策树 → 主课型 + 强化课型
> 依赖：所有 MDF 骨架须同时满足 `pedagogy.md`（ABT / 五透镜 / 脚手架 / 诊断反馈 / 变量策略 / 视觉-文本协调）与 `markdownflow.md`（交互语法）约束
> 用途：导师/agent 按课型模板快速生成结构正确的企业课程，避免「什么课都长一样」。

---

## 〇、五种课型总览

| # | 课型 | key | MDF 骨架 | 核心交互 | 评估方式 | 典型场景 |
|---|------|-----|----------|----------|----------|----------|
| 1 | 入职型 | `onboarding` | 规则 → 流程演示 → 情景判断 → 承诺确认 | 单选情景判断 + 承诺确认 | 情景判断题通过 | 新员工上岗 |
| 2 | 产品型 | `product` | 认知 → 机制 → 对比 → 应用 → 话术演练 | 对比单选 + 应用输入 | 应用输出检查 | 产品知识 / 新品 |
| 3 | 合规型 | `compliance` | 规则 → 红线案例 → 边界判断 → 场景决策 → 签署 | 边界判断 + 签署确认 | 决策正确率 + 签署回执 | 合规 / 制度 / 红线 |
| 4 | 演练型 | `practice` | 拆解 → 示范 → 提示练习 → 独立演练 → 诊断反馈 | 输入 + 三层脚手架 | 独立演练评分 | 操作技能 / 话术 |
| 5 | 案例研讨型 | `case` | 案例 → 分析引导 → 决策选项 → 复盘对比 | 分支决策 + 复盘输入 | 决策理由 + 复盘质量 | 管理 / 销售场景 |

> 组合规则：主课型 +（可选）强化课型。例：`practice` + `product`（销售演练配产品认知课）。
> 一门课程的每课只能有一个课型，但整门课程可分段混合（Q4=series/system 时）。

## 一、入职型（onboarding）

### 适用场景
- 新员工上岗、转岗、新系统上线首学。
- 目标是「快速进入岗位、遵守规则、能走通主流程」。

### MDF 骨架（结构段）

```
1. ABT 开头（已知工作场景 → 但新手常踩的坑 → 因此先懂规则和流程）
2. 规则段     — 公司/岗位核心规则，逐条讲清「是什么、为什么」
3. 流程演示段 — 主流程分步演示（视觉-文本协调：每步配图 + 说明）
4. 情景判断   — 3~5 个真实工作情景，单选判断「该怎么做」
5. 承诺确认   — 关键承诺点（守时/合规/安全）让学员逐条确认
6. 小结 + 下一步指引
```

### 推荐交互类型
- 单选情景判断 `?[%{{situation_choice}} A | B | C]`（每个情景一个判断点）
- 承诺确认 `?[%{{commit_1}} 我承诺遵守 | 我了解但不确定]`（真实承诺，不设「我不承诺」诱导项）

### 评估方式
- 情景判断题正确率 ≥ 80% 通过；错题走诊断反馈分支后重做。
- 承诺确认项全部勾选（记录式，不算分数）。

### 禁止事项
- ❌ 一节课塞 10 条以上规则（信息过载，违反 lesson-loop 密度约束）。
- ❌ 只讲规则不给情景练习（规则不落地 = 等于没学）。
- ❌ 承诺确认做成「形式化勾选」无反馈（应结合具体情景复述承诺含义）。

### 示例片段（MDF）
```markdown
## Objective
确认学员能在 3 类日常情景中选择符合制度的处理方式。

情景：你早上收到一份需要领导签字的文件，但领导出差 3 天。
?[%{{approval_choice}} 等领导回来再签 | 找代理审批人 | 自行代签]
Restate the learner's current choice as {{approval_choice}}.
若选「自行代签」→ 诊断：代签违反签批制度，属越权行为……
```

## 二、产品型（product）

### 适用场景
- 产品知识、新品上市、方法学/原理讲解、知识体系建立。
- 目标是「建立正确认知 → 能向外讲清 → 能应对客户问题」。

### MDF 骨架（结构段）

```
1. ABT 开头（客户见过的现象 → 但常见认知误区 → 因此搞懂产品机制）
2. 认知段   — 产品是什么、解决什么问题（先「为什么重要」再「是什么」）
3. 机制段   — 工作原理/核心机制（难概念用五透镜法：看现象→拆原理→讲机制→对比→迁移）
4. 对比段   — 与竞品/旧方案/替代品对比（对比单选交互）
5. 应用段   — 典型应用场景 + 边界（哪些情况不适用）
6. 话术演练 — 把认知转成对外话术（输入交互，落到可复用话术）
```

### 推荐交互类型
- 对比单选 `?[%{{compare_answer}} 方案A | 方案B]`（检验「对比差异」理解）
- 应用输入 `?[%{{use_case}} ...写一个适用场景`（迁移应用，配诊断反馈）

### 评估方式
- 应用输出检查：学员给出场景/话术，agent 按 checklist（准确/完整/可执行）反馈。
- 对比题正确率 ≥ 80%。

### 禁止事项
- ❌ 只讲参数堆参数（没有客户价值视角，成人学员会流失）。
- ❌ 产品卖点未配适用边界（学员会无差别推荐，造成信任损失）。
- ❌ 机制讲解一长段不分段（用五透镜法拆成独立段）。

### 示例片段（MDF）
```markdown
机制讲解（五透镜：Compare 透镜）
与离心法相比，本方法在批量样本下用时更短，但对操作环境要求更高。
?[%{{method_compare}} 离心法更快 | 本方法适合批量 | 两者没有区别]
Restate the learner's current choice as {{method_compare}}.
若选「本方法适合批量」→ 正确，本方法通量优势明显……
```

## 三、合规型（compliance）

### 适用场景
- 法规/制度/红线/安全/数据合规培训。
- 目标是「知道红线在哪 → 能在边界场景做对决策 → 留痕确认」。

### MDF 骨架（结构段）

```
1. ABT 开头（日常操作里的一次「差点违规」→ 违规后果 → 因此学规则）
2. 规则段   — 明文规则逐条讲清（引用原文，不得转述失真）
3. 红线案例 — 2~3 个真实/典型违规案例，讲清「错在哪、后果、正确做法」
4. 边界判断 — 灰色地带场景，单选判断「合规/违规/需请示」
5. 场景决策 — 综合场景决策题（多步：判断→选择→给理由）
6. 签署确认 — 学员确认「已理解并承诺遵守」，留回执
```

### 推荐交互类型
- 边界判断单选 `?[%{{boundary_judge}} 合规 | 违规 | 需请示`（必设「需请示」选项，避免二选一逼判断）
- 签署确认（记录式）+ 决策理由输入（综合场景）

### 评估方式
- 边界判断正确率 ≥ 100%（合规零容忍）——答错必须走诊断反馈直至答对。
- 签署确认记录留档（回执）。

### 禁止事项
- ❌ 规则转述走样（必须贴近原文，医疗垂类叠加 immutable 规则）。
- ❌ 边界判断只有「合规/违规」两选项（真实工作常需「请示」，二选一诱导误判）。
- ❌ 无签署环节（合规培训的核心留痕缺失）。
- ❌ 案例做成「猎奇故事」而无后果教育。

### 示例片段（MDF）
```markdown
客户微信发来一份含个人信息的名单，让你帮忙核对是否符合投保资格。
?[%{{data_boundary}} 可以核对 | 违规，拒绝 | 需请示数据合规负责人]
Restate the learner's current choice as {{data_boundary}}.
若选「违规，拒绝」→ 需补充：直接拒绝前应说明原因并引导走正规渠道……
```

## 四、演练型（practice）

### 适用场景
- 操作技能、话术演练、流程走通、软件操作。
- 目标是「学员能独立完成 → 动作达标 → 形成肌肉记忆」。

### MDF 骨架（结构段）

```
1. ABT 开头（一次操作失误导致的后果 → 因此把操作练到位）
2. 拆解段   — 任务拆成步骤（分步讲清每步要点）
3. 示范段   — 完整示范（三层脚手架第 1 层：全示范）
4. 提示练习 — 给提示/半成品让学员补全（第 2 层：部分提示）
5. 独立演练 — 无提示独立完成（第 3 层：独立尝试）
6. 诊断反馈 — 按 checklist 逐项反馈 + 错项诊断
```

### 推荐交互类型
- 输入交互 `?[%{{practice_input}} ...写出第X步/完整话术`（演练核心）
- 分层练习：示范 → 提示 → 独立（每课至多一个完整脚手架序列）

### 评估方式
- 独立演练评分（rubric：步骤完整性 / 准确性 / 流畅度）。
- 诊断反馈：每个错误点给出「为什么错 + 正确做法」，不循环同一题。

### 禁止事项
- ❌ 只示范不演练（学员看懂了 ≠ 会做）。
- ❌ 演练无反馈（学员练错方向，形成错误肌肉记忆）。
- ❌ 一次给多个演练任务（每课一个核心演练）。
- ❌ 独立演练无后续交互（死胡同题，违反 pedagogy 约束）。

### 示例片段（MDF）
```markdown
独立演练：现在请独立完成一次完整异议处理话术。
?[%{{full_response}} ...写下你应对「太贵了」异议的完整话术]
Restate the learner's current choice as {{full_response}}.
按 checklist 反馈：共情？举证？引导？缺哪步给哪步的诊断……
```

## 五、案例研讨型（case）

### 适用场景
- 管理决策、销售场景、复杂问题、复盘类培训。
- 目标是「在真实复杂场景中练习判断与决策 → 通过对比复盘提升决策质量」。

### MDF 骨架（结构段）

```
1. ABT 开头（真实场景引入：一个管理者面临的棘手局面）
2. 案例段   — 完整案例背景（人物/情境/约束/目标）
3. 分析引导 — 引导学员抓关键矛盾（提问式，不直接给答案）
4. 决策选项 — 给出 2~3 个决策方案，单选「你会怎么选」
5. 分支讲解 — 按选择分支：分析该决策的利弊/后果
6. 复盘对比 — 展示「实际怎么做」+ 让学员对比自己的选择，输入复盘
```

### 推荐交互类型
- 分支决策单选 `?[%{{decision}} 方案A | 方案B | 方案C`（必须分支讲解）
- 复盘输入 `?[%{{review}} ...对比你的选择与实际做法的差异`

### 评估方式
- 决策理由质量（是否识别关键矛盾 / 是否考虑约束 / 是否可落地）。
- 复盘深度（是否发现认知盲区）。

### 禁止事项
- ❌ 案例过虚（无具体人物/数字/约束，学员无法代入）。
- ❌ 决策题只有唯一「标准答案」（管理场景通常多解，重点是理由质量）。
- ❌ 无复盘对比（案例研讨的价值在对比中产生）。
- ❌ 一次给多个案例（每课一个深入案例）。

### 示例片段（MDF）
```markdown
你带的销售新人连续 3 周未开单，情绪低落，你面临：
A 单独辅导话术  B 调整客户资源  C 先观察一周
?[%{{mgmt_decision}} A | B | C]
Restate the learner's current choice as {{mgmt_decision}}.
若选 A → 优势是直接补短板，但需先判断是能力问题还是资源问题……
复盘：实际案例中主管选择了 B（先诊断再干预）。请对比你的选择：
?[%{{mgmt_review}} ...说明你的选择与实际做法的差异及原因]
```

## 六、通用约束（所有课型必须遵守）

1. **ABT 开头**：每课以 `已知 → 冲突 → 为什么学` 三拍开场，先于学习目标陈述（`pedagogy.md#pattern-d`）。
2. **最小教学闭环**：setup → explanation → interaction → close，四段缺一不可（`pedagogy.md#lesson-loop`）。
3. **交互语法**：只用单/多选、输入、分支四类；`?[]` 独立成行；问题在交互行之前；选项与叙述一致（`markdownflow.md#interactions`）。
4. **变量策略**：每课 ≤5 个交互，每交互必须有下游效果（分支/反馈/难度变化）（`pedagogy.md#variable-strategy`）。
5. **诊断反馈**：每个错误选项给具体诊断，不循环同一题（`pedagogy.md#diagnostic-feedback`）。
6. **视觉-文本协调**：核心概念配图描述 + 文字完整解释（`pedagogy.md#visual-text-coordination`）。
7. **医疗垂类**：`domain == "medical_ivd"` 时叠加医学分段规则，参考值/术语 immutable（`pedagogy.md#medical-vertical-segmentation-rules`）。

## 七、出口 tag 映射

每课完成课型模板生成后，整门课程按入口决策打 tag（详见 `task-driven-design.md#四、出口`）：

- `lesson_type:<主课型 key>` → 写入 `course_position_tags.tag`
- `task:<业务任务>` → 写入 `course_position_tags.tag`（与 lesson_type 竖线拼接）
- `role:<岗位>` → 写入 `course_position_tags.position`

课型 key 与 tag 值：`onboarding` / `product` / `compliance` / `practice` / `case`。
